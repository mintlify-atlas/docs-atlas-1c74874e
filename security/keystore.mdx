The wolfBoot keystore holds the public keys that the bootloader uses to verify firmware signatures. At boot time, wolfBoot selects the key slot that matches the signing key referenced in the image manifest, checks that the key has permission for the target partition, and verifies the signature.

## What the keystore is

The keystore is generated by the `keygen` tool and compiled into the wolfBoot image as `src/keystore.c`. It contains an array of `keystore_slot` structures — one entry per trusted public key.

```c
struct keystore_slot {
    uint32_t slot_id;       /* sequential slot index, starting from 0 */
    uint32_t key_type;      /* algorithm, e.g. AUTH_KEY_ECC256 */
    uint32_t part_id_mask;  /* partition permission bitmask */
    uint32_t pubkey_size;   /* size of the public key buffer */
    uint8_t  pubkey[KEYSTORE_PUBKEY_SIZE]; /* raw public key */
};
```

The header is 16 bytes (`KEYSTORE_HDR_SIZE`). Each slot is `KEYSTORE_HDR_SIZE + KEYSTORE_PUBKEY_SIZE` bytes.

The `keygen` tool also writes a `keystore.img` binary that can be used for external keystore storage in place of the compiled-in `src/keystore.c`.

## Generating keys

### Single key

Running `make` for the first time automatically generates a single `wolfboot_signing_private_key.der` and the corresponding `src/keystore.c`. To generate a key manually:

```bash
./tools/keytools/keygen --ecc256 -g wolfboot_signing_private_key.der
```

Supported algorithm flags: `--ed25519`, `--ed448`, `--ecc256`, `--ecc384`, `--ecc521`, `--rsa2048`, `--rsa3072`, `--rsa4096`, `--lms`, `--xmss`, `--ml_dsa`.

### Exporting the public key

Use `--exportpubkey` together with `-g` to save both the private and public keys to DER files:

```bash
./tools/keytools/keygen --ecc256 --exportpubkey -g mykey.der
# Creates: mykey.der (private) and mykey_pub.der (public)
```

### Importing an existing public key

If the private key lives in an HSM and you only have the public key, import it without generating a new private key:

```bash
./tools/keytools/keygen --rsa2048 -i rsa2048_pub.der
```

## Multiple keys

`keygen` accepts multiple `-g` and `-i` options in a single invocation. All keys are written to the same `src/keystore.c`:

```bash
# Generate two Ed25519 keypairs in one command
./tools/keytools/keygen --ed25519 -g first.der -g second.der
```

The resulting `src/keystore.c` contains both public keys:

```c
#define NUM_PUBKEYS 2
const struct keystore_slot PubKeys[NUM_PUBKEYS] = {

    /* Key associated to private key 'first.der' */
    {
        .slot_id = 0,
        .key_type = AUTH_KEY_ED25519,
        .part_id_mask = KEY_VERIFY_ALL,
        .pubkey_size = KEYSTORE_PUBKEY_SIZE_ED25519,
        .pubkey = {
            0x21, 0x7B, 0x8E, 0x64, 0x4A, 0xB7, 0xF2, 0x2F,
            /* ... */
        },
    },

    /* Key associated to private key 'second.der' */
    {
        .slot_id = 1,
        .key_type = AUTH_KEY_ED25519,
        .part_id_mask = KEY_VERIFY_ALL,
        .pubkey_size = KEYSTORE_PUBKEY_SIZE_ED25519,
        .pubkey = {
            0x41, 0xC8, 0xB6, 0x6C, 0xB5, 0x4C, 0x8E, 0xA4,
            /* ... */
        },
    },
};
```

### Keys of different types (universal keystore)

By default, wolfBoot enforces a single algorithm type across the entire keystore. Enable `WOLFBOOT_UNIVERSAL_KEYSTORE=1` to allow mixed algorithm types:

```bash
./tools/keytools/keygen --ecc256 -g a.key \
                        --ecc384 -g b.key \
                        --rsa2048 -i rsa-pub.der
```

<Note>
  `WOLFBOOT_UNIVERSAL_KEYSTORE=1` is required for [hybrid post-quantum signatures](/security/post-quantum#hybrid-mode-classic--pq).
</Note>

## Partition permissions

Each key slot carries a `part_id_mask` bitmask that controls which firmware partitions the key may authenticate. By default this is `KEY_VERIFY_ALL`.

Partition IDs are assigned as follows:
- Bit 0 — wolfBoot self-update partition
- Bit 1 — main firmware partition (default)
- Bits 2+ — additional partitions

Restrict a key to specific partitions using `--id`:

```bash
# generic.key can verify any partition; restricted.key only partitions 1, 2, and 3
./tools/keytools/keygen --ecc256 \
    -g generic.key \
    --id 1,2,3 -g restricted.key
```

## Key rotation strategy

wolfBoot does not have a built-in revocation mechanism, but you can achieve key rotation by:

1. Adding the new public key to the keystore while keeping the old one.
2. Signing the next firmware update with the new private key.
3. Once all devices have installed the new firmware, removing the old key from the keystore in a subsequent wolfBoot self-update.

<Warning>
  A wolfBoot self-update that removes a key is irreversible after it is installed. Test your new key thoroughly before deploying a keystore that excludes the old one.
</Warning>

## Keystore interface API

When `src/keystore.c` is linked directly, wolfBoot uses it via the following API (declared in `include/keystore.h`):

```c
/* Number of key slots in the keystore */
int keystore_num_pubkeys(void);

/* Size in bytes of the public key in slot id */
int keystore_get_size(int id);

/* Pointer to the public key buffer for slot id */
uint8_t *keystore_get_buffer(int id);

/* Algorithm type for slot id */
uint32_t keystore_get_key_type(int id);

/* Partition permission mask for slot id */
uint32_t keystore_get_mask(int id);
```

## External keystore

To store the keystore outside of the wolfBoot binary (e.g., in external NVM or a key vault), implement the interface above in a custom driver and link it instead of `src/keystore.c`.

The `keystore.img` binary produced by `keygen` can be written to any storage medium. Your driver reads from that medium and returns data through the API.

## Keys stored in an HSM (inaccessible key material)

When using wolfHSM or another HSM where the private key never leaves the device, the `pubkey` field in the keystore does not need to contain the actual key material. Use `--nolocalkeys` to generate a keystore entry with a zeroed `pubkey` buffer:

```bash
./tools/keytools/keygen --ecc256 --nolocalkeys -g hsm_key_ref.der
```

## Build system integration

Running `make` without pre-existing keys auto-generates a single keypair for development. To use your own keys in a test app build without manually running `keygen -i`:

```bash
make USER_PRIVATE_KEY=/path/to/my-key.der USER_PUBLIC_KEY=/path/to/my-pubkey.der
```

<Tip>
  For production, always generate keys outside of the build system and commit only `src/keystore.c` (the public key) to version control. Never commit private key DER files.
</Tip>
